# UNPS File Routing & Human-Readable Workspace Standard

Status: Candidate  
Version: 0.1.0  
Owner: Unparalleled Source

## Purpose
Ensure every file created, imported, moved, normalized, or generated by an agent is routed to the correct client, project, opportunity, or internal workspace and remains understandable to a human without requiring an AI session, hidden database, or proprietary index.

## Core Rule
Before any persistent file write, resolve **who the file belongs to, what work it supports, what authority/status it has, and where a human would expect to find it**.

Never create a new root or duplicate project tree when a suitable existing workspace already exists.

## Routing Gate
Before writing or moving a file, resolve these fields:
1. **Organization / owner** — UNPS, client, partner, internal function, or personal/admin scope.
2. **Client / account** — named client or `Internal`.
3. **Project / opportunity** — named project, solicitation, engagement, product, or operating initiative.
4. **Artifact class** — source, research, data, correspondence, working file, decision, deliverable, admin, or archive.
5. **Authority** — authoritative source, approved working artifact, draft, generated derivative, or reference.
6. **Lifecycle** — active, superseded, final, deprecated, or archived.
7. **Sensitivity / access** — ordinary project access or a more restricted location when required.

If the correct destination cannot be resolved with reasonable confidence, do **not** guess. Use the existing project intake/staging area or an explicit `_NEEDS_ROUTING` holding location, record why it is unresolved, and resolve it at the next workspace-hygiene pass.

## Preferred Human-Readable Hierarchy
Adapt only when the project already has an established structure.

```text
<Client_or_Internal>/
└── <Project_or_Opportunity>/
    ├── 00_README/
    ├── 01_SOURCE_OF_TRUTH/
    ├── 02_RESEARCH/
    ├── 03_DATA/
    ├── 04_WORKING/
    ├── 05_CORRESPONDENCE/
    ├── 06_DECISIONS/
    ├── 07_DELIVERABLES/
    ├── 08_ADMIN/
    └── 99_ARCHIVE/
```

Do not impose this tree on a mature workspace if doing so would create churn. Map the semantic roles to the existing structure instead.

## Root Readability Contract
Every active project should expose enough human-readable orientation that a new team member can understand the workspace quickly. Prefer:
- `README.md` — purpose, status, owner, key links, structure, how to work in the folder;
- `PROJECT_INDEX.md` — key artifacts and canonical locations when the project is complex;
- `STATUS.md` — current state, major blockers, next milestones;
- `DECISIONS.md` or ADRs — durable decisions and rationale;
- `LEARNINGS.md` — validated project-specific lessons when useful.

Use Google-native documents for collaboration when appropriate, but keep durable machine/agent instructions in Markdown or plain text whenever practical.

## Naming Rules
- Use descriptive human names; do not expose opaque IDs as the primary title.
- Preserve official solicitation, contract, opportunity, customer, and product identifiers in names when they aid retrieval.
- Use ISO dates (`YYYY-MM-DD`) when chronology matters.
- Use version numbers only when the workflow genuinely needs parallel versions; otherwise prefer one canonical working file plus revision history.
- Mark published/final artifacts clearly when ambiguity would matter.
- Avoid names such as `final-final-v2-new`, `document1`, `copy`, `untitled`, or unexplained abbreviations.

## Authority & Duplicate Control
- Preserve authoritative originals.
- Normalize heavy sources into Markdown/text derivatives for repeated AI ingestion, but never mistake the derivative for the authoritative signed/visual original.
- Prefer one canonical file over multiple nearly identical copies.
- When a newer artifact supersedes an old one, update indexes/references and move the old artifact to `99_ARCHIVE` rather than leaving competing versions active.
- Never silently delete source-of-truth material solely because a normalized copy exists.

## File-Move Safety
Before moving or renaming an established artifact:
1. verify its current project/client;
2. check whether other files, prompts, calendars, emails, or docs reference it;
3. update critical references when practical;
4. preserve revision history or provenance;
5. avoid changing a user's deliberate organization without a clear benefit.

## Cross-Project Rule
A reusable framework, skill, prompt, template, or methodology belongs in the shared UNPS library only when it is truly reusable. Project-specific facts stay in the project workspace. Do not leak client-specific content into generic skills or templates.

## Routing Confidence
Use three internal confidence levels:
- **High** — destination is explicit or clearly established.
- **Medium** — strong contextual match; verify against project index/workspace before writing.
- **Low** — ambiguous; stage rather than misfile.

## Human Test
Before closing a file-management task, ask:
> Could a competent human who did not see this chat find this file, understand what it is, know whether it is current, and understand where related material lives?

If not, improve routing, naming, indexing, or documentation.
