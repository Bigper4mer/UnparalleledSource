# Contributing to HiveForge

HiveForge grows from demonstrated UNPS workflows—not speculative instruction accumulation.

## Contribution standard

A proposed asset should include:

- the problem it solves;
- a clear trigger or use case;
- required inputs;
- dependencies and connector needs;
- expected output;
- failure and uncertainty behavior;
- evidence that it does not duplicate an existing asset;
- a representative test or evaluation;
- provenance for external patterns.

## Maturity

New assets begin as `experimental` or `candidate`.

`experimental → candidate → production → deprecated`

Production requires repeatable evidence across real work. A polished description is not a promotion gate.

## Pull requests

Keep changes narrow and explain:

1. What changed
2. Why it changed
3. What was verified
4. Security or data-handling impact
5. Context/token impact
6. Maturity impact

Never include secrets or private UNPS/client material in a contribution.
